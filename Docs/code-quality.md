# Проверки качества кода

Проверки запускаются на JDK 17 через Gradle Wrapper 8.14. Для линтинга не нужны
Telegram-токен, `.env` или PostgreSQL. Версии инструментов закреплены в корневом
`build.gradle.kts`: ktlint-gradle 12.1.2, ktlint 1.3.1 и detekt 1.23.8.

## Запуск

Из корня проекта в PowerShell:

```powershell
# Единая проверка стиля и структуры во всех модулях
.\gradlew.bat lint

# Отдельные инструменты или один модуль
.\gradlew.bat ktlintCheck detekt
.\gradlew.bat :core:ktlintCheck :core:detekt

# Проверки качества, тесты и компиляция точки входа
.\gradlew.bat lint :core:test :data:test :app:compileKotlin --continue

# Автоформатирование (меняет файлы, после запуска проверьте diff)
.\gradlew.bat ktlintFormat
```

В Linux/macOS используйте `./gradlew` вместо `.\gradlew.bat`.
`check` и `build` также включают линтеры. При нарушении нового правила сборка
завершается с ошибкой: `ignoreFailures` не используется для обхода проверок.
GitHub Actions запускает проверку на каждом push и pull request, сохраняет отчёты.

## Область проверки

ktlint проверяет Kotlin во всех source set каждого модуля и Gradle Kotlin DSL,
включая корневые `build.gradle.kts` и `settings.gradle.kts`. `.editorconfig` задаёт
единый стиль ktlint official: четыре пробела, длина строки 120, завершающие
запятые и явные импорты.

detekt анализирует все `.kt` и `.kts` внутри `src` каждого модуля:

- `app`: точку входа, dispatch и фоновые задачи;
- `core`: роутеры всех разделов, клавиатуры, экраны, сессии, обработчики и мини-игры;
- `data`: репозитории, схемы, сервисы, API, модерацию и обработку изображений;
- Kotlin-тесты всех модулей, включая `app`, где выполнение тестов отключено.

Каталоги отдельных функций не исключаются. Сгенерированные `build` и `.gradle`
не входят в линтинг. Java smoke-тесты проверяются компилятором Java, эти два
линтера анализируют только Kotlin.

detekt использует стандартные правила с настройками из `config/quality/detekt.yml`:
именования, потенциальные ошибки, пустые блоки, обработка исключений, сложность,
размер классов и функций, число параметров и вложенность. Предел длины функции —
60 строк, цикломатической сложности — 15, вложенности — 4. Включена проверка
`GlobalCoroutineUsage`. Правила оформления принадлежат ktlint; дублирующие проверки
длины строки и wildcard-импортов в detekt отключены. MagicNumber отключён, поскольку
в проекте много UI-размеров, SQL и игровых констант; запрета TODO-комментариев нет.

Единая задача `lint` запускает detekt без разрешения типов, чтобы не требовать
компиляции приложения. Правила detekt, которым нужно разрешение типов, этим
запуском не проверяются. Компиляция и тесты дополняют линтеры: они по-прежнему
необходимы для проверки бизнес-логики, SQL-транзакций и Telegram-сценариев.

## Существующие нарушения

`config/quality/baselines/` хранит списки нарушений на момент подключения
инструментов: отдельный файл ktlint для корня и каждого модуля и detekt для каждого
модуля. Это позволяет внедрить проверки без массового изменения существующего кода.
Новые файлы и новые нарушения в существующих файлах проверяются автоматически.
Совпадающие с baseline нарушения остаются допустимыми, в том числе в изменённой
функции. Baseline не является проверкой только изменённых строк.

Не пересоздавайте baseline при обычной ошибке линтера: исправьте код. При
плановом устранении долга можно обновить соответствующий baseline и проверить,
что diff только удаляет исправленные нарушения. Команды первоначальной генерации:

```powershell
.\gradlew.bat ktlintGenerateBaseline detektBaseline
```

Генерация baseline не входит в `lint`, `check`, `build` или CI. `ktlintFormat`
игнорирует baseline и может переформатировать весь проект: запускайте его отдельно
от функциональных изменений и проверяйте состав правок перед коммитом.

## Отчёты и параллельная работа

Отчёты ktlint находятся в `build/reports/ktlint` корня и каждого модуля, detekt —
в `<модуль>/build/reports/detekt` (HTML, XML, SARIF). В CI они доступны в артефакте
`quality-reports`, в том числе после неуспешной проверки.

Не запускайте конкурирующую сборку в каталогах работающего dev-watcher.
Остановите watcher либо используйте отдельный Gradle init script, перенаправляющий
`layout.buildDirectory` всех проектов, и отдельный `--project-cache-dir`.
Запуск линтеров не требует запуска бота.
